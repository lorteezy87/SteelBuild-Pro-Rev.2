# Reviewed commercial writes — isolated verification

Run `npm ci` and `npm test` in this directory. The pinned PGlite dependency creates only in-memory synthetic data. The suite uses captured staging lifecycle functions, financial guards, SOV CHECK constraints, and actual SOV audit and timestamp trigger definitions. Its project-member RLS fixture is deliberately minimal; full deployed policy review remains separate.

Candidates remain subject to manual reviewed application/stamping:

- `20261007113400_reviewed_change_order_saves.sql`: change-order metadata and lifecycle effects use the reviewed version/status/amount in one transaction.
- `20261007120658_reviewed_sov_item_saves.sql`: ordinary SOV updates use the reviewed timestamp so an old editor cannot overwrite a later CO adjustment. This filename was generated by `supabase migration new reviewed_sov_item_saves` using pinned CLI 2.81.3; candidate SQL was transferred byte-for-byte before verification.

## SOV API contract

`save_sov_item_reviewed(p_id uuid, p_expected_updated_at timestamptz, p_patch jsonb) returns jsonb`

The return is the full current SOV row. Callers must retain the exact `updated_at` shown when opening the draft, including fractional seconds, and pass it with the attempted edit. A legacy null version is valid only when the database version is also null. SQLSTATE `40001` means reload and review the newer financial value before saving; clients must not substitute a fresh version automatically.

Allowed editable fields: `description`, `scheduled_value`, `previous_percent_complete`, `current_percent_complete`, `retainage_percent`, `status`, `application_number`, `period_from`, `period_to`, `submitted_date`, `payment_received_date`, `cost_code`, `cost_code_name`, `cost_code_id`, `work_package_id`, `sort_order`. Official identifiers, project scope, timestamp/author fields, deletion flags, `metadata` and `change_order_id` are excluded. CO lifecycle provenance stays with its existing workflow. This function does not add a new billing approval workflow; the existing SOV register statuses remain valid.

The invoker function locks the current SOV row, checks active workspace membership, project access, PM role, MFA and the expected version, then validates the proposed ordinary fields. Existing RLS, cost-row guard, CHECK constraints, audit and timestamp triggers run normally. It does not enable an RPC bypass flag or accept a client timestamp. New references must belong to the active project; unchanged archived links may remain on historical rows.

The suite reproduces the previous $1,000 → $1,400 approved adjustment → stale $1,000 overwrite, then proves the reviewed save rejects the same overwrite without retaining partial metadata. It also checks current edits, audit/version advancement, immutable provenance, grants/roles/workspace removal/archive/MFA, invalid dates and financial values, nullable legacy versions, and historical references.

Real PostgreSQL CI additionally overlaps CO approval with a blocked stale SOV editor, and two SOV editors holding the same reviewed revision. These tests require distinct backend sessions waiting on a held row lock; local PGlite passing does **not** establish real concurrency acceptance. See `../commercial-postgres/README.md`.
