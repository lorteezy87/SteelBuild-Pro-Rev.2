Status vocabulary:

- **Open — source/catalog:** a current boundary or implementation gap was observed; live exploitability may depend on stated configuration.
- **Ready — not released:** a correction exists with local evidence; hosted/client release and acceptance remain open.
- **Partial:** some controls are verified; the specifically named remainder stays open.
- **Verified control:** bounded evidence supports the named control, without implying adjacent controls are secure.
- **Unverified:** required external configuration or an operational exercise has not been observed. This is an assurance gap, not a fabricated vulnerability.
- **Design requirement:** required before a new capability ships; absence is not described as a defect in an unbuilt feature.

Priority means remediation order: P1 before sensitive release/tenant expansion; P2 next hardening tranche; P3 maintenance. No blanket P0 or “all secure” verdict is issued by this review.

#### EDGE-9 expanded — send quota is bypassable through editable correspondence rows

- **Severity/status:** Medium; confirmed source defect. Expand existing EDGE-9 rather than create a duplicate. It is stronger than the historical concurrency-only concern.
- **Evidence:** `supabase/functions/email-send/index.ts:159-181` counts `email_messages` by `sent_by`, `direction=outbound`, and `sent_at`. ### Priority findings and acceptance criteria

#### AUTH-4 — recovery session can still escape the recovery UI (Medium, source-confirmed open)

- Evidence: `src/lib/AuthContext.tsx:122` holds recovery state only in React; `:320` sets it only for `PASSWORD_RECOVERY`; bootstrap at `:305` obtains the persisted session. `src/pages/UpdatePassword.jsx:91` Cancel reloads `/`. `src/boot/AuthenticatedApp.jsx:77` only gates on the volatile flag. `AuthContext.tsx:442-445` clears it immediately after password update, before the page awaits logout (`UpdatePassword.jsx:38`), so a failed logout can also expose the full app after the password update.
- Prerequisites/impact: a valid emailed recovery session on a non-MFA account, or a session that meets MFA, followed by Cancel/reload. This bypasses the intended reset-only UI, not an arbitrary-password or MFA bypass. Supabase recovery establishes a real session; the client comment calling it recovery-scoped is inaccurate.
- Remediation: maintain recovery state across reload/tab navigation, derive it from a validated auth callback flow, and make Cancel clear the recovery session. Keep the recovery screen until session termination is confirmed; explicitly handle failed sign-out. Do not rely on UI state as server authorization.
- Acceptance: actual AuthProvider + AuthenticatedApp tests for PASSWORD_RECOVERY → reload/Cancel, failed logout after successful update, and normal reset completion; verify a recovery session never mounts org/project routes during that lifecycle. Existing `src/boot/__tests__/AuthenticatedApp.test.jsx:130,156` tests gate priority only, not reload persistence.

#### AUTH-5 — implicit auth callbacks / transient token fragments (Medium, source-confirmed configuration; exploitation untested)

- Evidence: `src/lib/supabase.ts:13-16` enables persistence and URL detection without `flowType`. Installed `node_modules/@supabase/auth-js/src/GoTrueClient.ts:194` defaults to `implicit`; its URL session parser starts at `:3582`. `src/instrument.js:67,85` strips query strings but not URL fragments from events/fetch breadcrumbs.
- Prerequisites/impact: victim visits a valid crafted implicit-session callback belonging to another account; possible login CSRF/confused workspace uploads. A token-bearing fragment can also be present briefly before SDK cleanup; actual telemetry capture of one was not tested.
- Remediation: move confirmation/recovery flows together to PKCE, verify redirect allowlists and native/web recovery behavior, and scrub credential-bearing fragments in telemetry. Keep this under AUTH-5, not a duplicate token-storage issue.
- Acceptance: reject unsolicited implicit token fragments; valid PKCE reset/confirmation works; replayed code fails; telemetry fixtures redact both query and hash credentials. No live callback or token test was performed.

#### AUTH-6 residual A — device-global calculator business data (Medium, source-confirmed open)

- Evidence: `src/pages/CranePickCalculator.jsx:62,193` uses global `crane-pick-history`; `:453-505` saves load/configuration/crane model/serial/chart provenance snapshots. `src/components/calculators/useCalcTape.js:12-17` loads/persists the unowned key. `src/pages/SteelWeightCalculator.jsx:40-42,162-180` loads and persists unowned `calc:steelweight:rate`, `unit`, and `rows`. `src/lib/AuthContext.tsx:18-38` does not remove those keys on successful identity termination.
- Prerequisites/impact: A uses the calculator, signs out successfully, B signs in on the same browser/native WebView profile and opens the calculator; A's pick history / rate / running totals are displayed without a server read. Same-user company switching has the same effect. This is distinct from the crane fleet library, which is already org-keyed (`src/lib/crane/craneLibrary.ts:21-23,141-160`).
- Remediation: namespace private calculator data by verified user + company, keyed React boundary on scope changes, and explicit handling/export of ownerless legacy history without assigning it to the next login. Do not silently delete user-created history.
- Acceptance: A→B account, A→B company, sign-out/re-entry, and delayed local writes never expose another owner's rows; original owner can recover retained rows; legacy data is never automatically loaded into a verified scope. Map to AUTH-6/M38 residual, no duplicate closed project-cache issue.

#### AUTH-6 residual B — delayed callbacks can repopulate cleared data / retain old Undo (Medium, source-confirmed continuation; end-to-end exploit untested)

- Reachable evidence: Schedule route calls `useScheduleMutations` (`src/pages/Schedule.tsx:238`) and editor events call its mutation (`src/pages/schedule/ScheduleBody.tsx:256,295,308`). `src/pages/schedule/useScheduleMutations.ts:197-209` captures a snapshot and restores it unconditionally after an error; `:214-224` creates a success/Undo action whose `undoTaskUpdate` uses singleton `entities` at `:164`. `src/pages/FieldToday.jsx:109-136` has a similar unguarded rollback at `:128`. Production Notes create/update/delete snapshots restore without identity checks (`src/pages/productionNotes/useProductionNotesWorkspace.ts:111-170`).
- Boundary: `AuthContext.tsx:19` clears queries; `OrgContext.jsx:66` removes old workspace queries. Neither stops pending mutation callbacks. These callbacks lack the generation/mount guards now present in `ProjectCloseout.jsx:28-33,84-107`.
- Prerequisites/impact: an authorized A mutation is pending when account/company changes; old failure can reinsert A's complete cached rows after cleanup. Project/folder-specific keys reduce immediate ordinary-route exposure but do not remove the residue. An old Schedule Undo can perform an A-task operation using B's current auth if B also has permission; RLS still blocks a B who lacks it. A cached stale row is not protected by RLS. A normal-route unauthorized display was not reproduced in this audit; do not claim general cross-tenant server access.
- Remediation: use the Closeout owner-generation pattern at user action start, recheck after every await including cancelQueries, suppress old success/error/settled/Undo callbacks, and scope/cache keys where appropriate. Abort/pin multi-step work when identity changes.
- Acceptance: real callbacks/components + real QueryClient, deferred request settled after account/company change or same-company sign-out/re-entry; assert no old rows, toast, invalidation or Undo effects, including while cancelQueries awaits; retain current-owner rollback/Undo behavior. Include online FieldToday fallback and Production Notes create/update/delete.
- Exclusions: `useDrawings` and `useSubmittals` contain similar optimistic code but the current hub consumes their reads only (`DrawingSubmittalHub.tsx:249-253`); do not count their unused mutation outputs as independently reachable findings. Closeout's focused fix is already committed (`219aa4f3`), with 11 identity tests from the prior implementation phase; do not reopen that fixed module.

#### AUTH-6 residual C — export/download can present old-account data after switching (Medium, source-confirmed continuation; native runtime untested)

- Evidence: `src/components/settings/SystemTab.jsx:42-61` fetches projects, awaits an entire workspace export, then downloads/shares it with no identity or mount check. `src/lib/workspaceExport.ts:119-142` iterates projects through the mutable singleton client's `exportProject` at `:58-60`. `src/pages/Documents.jsx:415-423,445-465` resolves URLs asynchronously and then presents files. `src/lib/native/fileExport.ts:242-245` awaits downloads before opening a share sheet, with no owner-generation check/cancellation.
- Prerequisites/impact: A starts a slow export/download; A signs out or changes company before it finishes; completion can still offer/download A's data to the current shared-device operator. Authorization at original fetch time does not prevent this late local presentation. Later iterations can also run with a different current JWT, though server RLS still controls each request.
- Remediation: capture identity/company before work, abort further fetching on changes, pin a request client where multi-step exports need it, discard results and skip download/share/toasts once stale; retain native temporary-file cleanup. Treat already intentionally downloaded/shared files as outside app recall.
- Acceptance: defer workspace export and native download, change owner before resolution, assert no browser anchor/native share/next request; current identity export remains usable, partial failures remain honestly reported, cached temporary files are deleted on cancellation.

#### AUTH-7 — automatic desktop refresh-token handoff (Medium, source-confirmed open; conditional exploit)

- Evidence: `src/pages/DesktopConnect.tsx:178-215` parses URL-supplied public key/state/challenge, obtains session, encrypts access + refresh token (`:203-205`) and creates handoff in a mount effect; only afterward does `:216` test whether the component is still active. The explicit link at `:260` opens an already-created handoff; it is not consent before exporting credentials.
- Prerequisites/impact: signed-in user follows attacker-controlled valid handoff query. It causes encrypted token export without explicit approval; obtaining/redeeming the one-use callback code is an additional condition, so do not describe the page alone as unrestricted token theft. The new MFA boundary removes the original AAL1 UI race in source; it does not address handoff consent or stale-session cancellation.
- Remediation: explicit user gesture and device/key fingerprint before encryption/send, registered handshake state, session-generation checks after waits, review whether a narrower capability can replace a long-lived refresh token.
- Acceptance: page load makes no handoff; approve sends once for the current identity; cancel/unmount/switch prevents sending; altered challenge/key/state and replayed code fail. Existing handoff crypto/one-time server checks should be retained.

#### AUTH-8 — no fresh proof for sensitive account actions (Medium, source-open; dashboard policy unverified)

- Evidence: `src/lib/AuthContext.tsx:440-448` changes password without current password/nonce, `:503-508` unenrolls MFA without a fresh challenge; account-delete has current MFA validation at `supabase/functions/account-delete/index.ts:82-83`, but client confirmation is only typed email (`src/components/settings/DeleteAccountZone.jsx:42-45`). No fresh-auth age/nonce check found in these paths.
- Prerequisites/impact: access to an already authenticated session, including an unlocked shared device or stolen session satisfying required AAL. This is not an MFA bypass: the current server MFA helper narrows account deletion to a satisfied session when enrolled.
- Remediation/acceptance: require fresh credential verification/nonce (and MFA when enrolled) for password change, factor removal and destructive account/workspace actions; verify Secure Password Change provider setting. Tests reject old sessions/missing proof and permit freshly proved requests. Live Auth dashboard setting was not inspected by this client review.

#### SEC-2 — raw attachment links remain on active daily-log/punchlist screens (Low-Medium, source-confirmed sink; exploit runtime-unverified)

This bypasses `resolveFileUrl`'s trusted-host/storage signing boundary (`src/api/client/storage.ts:50-63`).

The read-only live HEAD found only Report-Only CSP; this source has prepared enforcement, so do not assume protection is already deployed.

#### SEC-3 — inbound email HTML still loads remote content (Low, source-confirmed open)

- Evidence: `src/pages/emailInbox/components.tsx:569-589` embeds verbatim rawHtml in srcdoc with `sandbox="allow-same-origin"`, no sanitizer or in-frame default-deny CSP/remote-image opt-in. Global source CSP `img-src ... https:` permits remote images; runtime deployed CSP state does not cure tracking pixels.
- Prerequisites/impact: an attacker emails a tracked body that a user opens; remote resources can reveal opening/IP and navigate the frame. No `allow-scripts` is present: do not label this confirmed script execution/XSS.
- Remediation/acceptance: sanitize allowed HTML, add restrictive srcdoc CSP, block remote images by default with deliberate load option. Test pixels/remote CSS/forms/meta refresh and ensure sandbox never adds allow-scripts while same-origin is retained.

#### SEC-4 — attachment MIME/content trust remains weak (Low, source-confirmed policy; delivered-file execution unknown)

- Evidence: `supabase/functions/email-ingest/index.ts:1026,1043` trusts attachment content type. `_shared/attachments.ts:15-24` blocks HTML/script extensions but not SVG. Baseline private bucket seeds allow SVG/XML/octet stream (`20260101000020_baseline_seed.sql:26-37`) and email-attachments has null MIME allowlist (`:44`). `src/lib/uploadValidation.ts:83` permits SVG for document/attachment workflows; all these UI guards are bypassable by an authorized API caller.
- Scope: potential active content/phishing on the Storage origin, not automatic access to the app's localStorage. Supabase delivered Content-Type/CSP/Content-Disposition and current bucket configuration need read-only live verification; no malicious object upload/open was done.
- Remediation/acceptance: server-side content classification, safe allowlists, attachment disposition for unsafe-to-inline formats, safe raster/PDF rendering. Test mismatched extension/MIME and SVG. Preserve normal construction document support and existing filename/size controls.

## Supplemental source reconciliation

### AUTH-9 / AUTH-10 — consent evidence versus functional onboarding

`src/lib/AuthContext.tsx:381-385` mints terms timestamp/version/acceptance in signup metadata. `supabase/migrations/20260101000010_baseline_schema.sql:867-877` copies profile identity/name from Auth metadata; this source review found no authoritative acceptance-event implementation. User-supplied metadata is not independent server evidence. AUTH-9 requires a server-owned versioned record with server timestamp and immutable provenance; simply copying a caller-chosen timestamp does not meet that requirement. The audit did not inspect real user metadata or make a legal enforceability determination. AUTH-10 remains functional invite-onboarding debt from the September report; no new security exploit was established.

### SEC-5 — decompression and signed-URL lifetime

`src/lib/ifc/gzip.js:16-18` materializes the complete decompressed stream with no output-byte cap; the viewer consumes this helper. Bound decompressed output and processing time, abort safely and test highly compressible synthetic input without uploading it. Impact is potential viewer resource exhaustion, not demonstrated server compromise. `src/hooks/useResolvedFileUrl.js:4,18-20,34` retains resolved URLs in a module-global map without TTL or owner namespace. Add expiration/owner invalidation and test stale cached links; current evidence does not show unauthorized discovery of another user's object reference. A signed URL already issued may remain valid for its configured lifetime even after role removal, so choose and test the intended revocation policy rather than assuming immediate invalidation.

The historical dead PDF-worker helper and non-security random suffix advice remain cleanup items, not active confirmed vulnerabilities. The Stripe prototype-key lookup has been corrected in source. WEB-5 delivery/cache/header observations remain host-specific availability and hardening work; absence of an optional header is not independently a vulnerability.
