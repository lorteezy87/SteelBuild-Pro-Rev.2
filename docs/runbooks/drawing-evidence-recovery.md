# Drawing observation export and archival recovery

Status: source candidate only. `supabase/candidates/drawing-source-observation-export.sql` is uninstalled. This document does not authorize a migration, hosted restore, deployment, ownership change or production write. The complete compatible package and authenticated staging acceptance are separate gates.

## Export contract

The caller-JWT `project-export` function retains its shared `export_version: 2` envelope, original tables, `files`, separate `storage_files`, and mandatory caller-attributed audit. `extensions.drawing_evidence` has independent `version: 1`, an explicit `observations` array (including zero rows), and `snapshot_token`. Workspace bundles retain their own version 1 and carry complete per-project extensions and failures unchanged. A missing reader or unknown reader version fails export; it never means inspected-empty.

`get_drawing_source_observations(project_id, after_receipt, after_drawing, snapshot_token, limit)` checks current project access and `steelbuild_security.satisfies_mfa()`. It does not require the PM mutation floor. The project soft-deletion visibility boundary applies; a status label such as “Archived” is not itself a new exclusion. Private observation/receipt table grants remain revoked, including from service_role. The function exposes neither the receipt's actor nor its request/replay UUID. `receipt_id` identifies the internal receipt row and is not its `request_id`.

Pages use the immutable `(receipt_id,drawing_id)` total order, with 1–500 rows per RPC. The first page establishes a SHA-256 fingerprint of the full visible identity roster scoped to its project. Every later page and the final verification use the same token; inserts, erasure, lost access, malformed cursors or duplicate rows fail the whole evidence read. The fingerprint and page are evaluated in one statement snapshot. The final check defines the evidence snapshot cutoff; the preexisting multi-table v2 export is not a cross-request repeatable-read database backup.

The project/cursor index bounds payload retrieval. Mutually exclusive first-page and cursor branches retain range index conditions under generic plans. The mandated fingerprint still scans every selected project identity on each page: **O(identity roster × page count)** work, not O(1). No history cap or truncation was added. The local 10,000-observation/30,000-other-project fixture and actual-query generic EXPLAIN catch foreign/prior-row payload rescans. PGlite timing does not prove PostgreSQL 17 or hosted 8-second statement-deadline margin. Exact-SHA PG17 CI and hosted staging maximum-history acceptance remain required before promotion. If those fail, stop for a reviewed strategy change; do not silently cap, cache or weaken consistency.

Each observation keeps the existing columns verbatim. Nullable text/source/page/version values stay null; `extracted_text: ""` and `callouts: []` retain inspected-empty meaning. JSON serialization alone collapses SQL NULL and JSON null, so `callouts_is_sql_null` preserves their distinction. Historical integer values are observations, not newly validated page assignments. `observed_current_revision_id` is an observed pointer, not a claim that extraction belongs to that revision. File paths/legacy absolute URLs are retained as evidence references and included in `files`. No URL is fetched and no retrieval proxy is introduced.

## Disposable archival rehearsal

Only the existing local PostgreSQL harness may positively execute `supabase/tests/drawing-set-revision-transaction/recovery.sql`. Its target must be the initially empty database named exactly `steelbuild_drawing_upload_test` on loopback, with the existing explicit fixture opt-in and empty-database census. The harness validates the PostgreSQL URL protocol, exact loopback hostname, exact database path and absence of query parameters before connecting; only after its initially-empty census succeeds does it set the distinct `drawing_recovery.client_loopback_verified` and `drawing_recovery.empty_fixture_verified` session markers. The script requires both markers to equal `yes`, the exact database name and a superuser operator. Missing/invalid markers reject recovery. These markers are trusted operator/harness assertions, not a hosted authorization boundary. PostgreSQL's server-interface address may be a container bridge when the validated client uses a loopback published port; no private-address range is allowed in place of the client preflight. PGlite must refuse this script; do not bypass the guard to get a green local result.

Run the repository's existing `npm test --prefix supabase/tests/drawing-set-revision-transaction` for PGlite behavior/refusal, and the existing `npm run test:postgres --prefix supabase/tests/drawing-set-revision-transaction` with the guarded disposable-loopback fixture settings for actual PG17 behavior, concurrency and recovery. Never point these settings at staging, production or a populated local database. Existing CI provides the PG17 environment. No credentials or customer exports are needed.

The harness supplies one temporary `drawing_recovery_input(envelope jsonb, remaps jsonb)` row in a transaction. `remaps` contains explicit `{kind: "project"|"set"|"drawing", original_id, destination_id}` records. The exported set/drawing relationships and existing synthetic destination relationships must agree. Missing relationships, foreign projects, duplicates, unknown extension versions, malformed values, inconsistent null flags and a roster/token mismatch reject the transaction. The target `drawing_observation_recovery` schema must not already exist.

Recovery creates only fixture-private `drawing_observation_recovery.remaps` and `.observations`. Each archived row keeps its complete original observation, original project/set/drawing/internal-receipt identities, snapshot token, mapped destination identities, recovered timestamp, and a separate SQL-null-aware callouts column. RLS is enabled; application schema/table grants are revoked. These are quarantined archival records and must be treated as imported evidence, not trusted operational authority. A roster fingerprint detects roster mismatch; it is not a signature proving export authenticity or immutable content.

The script never inserts into live `steelbuild_drawing_revision.source_observations`: its foreign key would require creating an operational receipt. It never creates such a receipt, engineering approval, release state or public restore RPC. The fixture compares every operational snapshot before/after, explicitly including unchanged requests and approvals. This is **archival recovery**, not a tested in-app restore or complete disaster recovery. Positive recovery/null/remap/rejection cases require the actual PG17 CI run; a PGlite refusal is not positive recovery evidence.

## Anonymization, retention and erasure

The fixture exercises actual foreign-key anonymization through deletion of its synthetic auth user: receipt `actor_id` becomes SQL NULL and business observations remain exportable to a remaining authorized member. It exercises the actual `soft_delete_project` helper: observations remain retained while the project is no longer visible. The actual `hard_delete_project` helper removes owned observations/receipts while preserving the unrelated synthetic project. The existing hash-checked `hard_delete_organization` and `erase_my_sole_member_workspaces` chain is also run and verifies observation erasure and preservation of the unrelated workspace.

Database erasure is not Storage-byte erasure; the existing SQL fixture explicitly retains the Storage object. Account session revocation, Storage purge, real PDF/page readback and a full hosted recovery are not established here. Privileged database/Storage administrators remain outside the ordinary-role immutability guarantee. Recovery archives and exported files are separate operator-held copies with their own disposal responsibilities; neither is automatically removed by application erasure.
